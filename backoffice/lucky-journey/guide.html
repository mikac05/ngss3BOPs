1. 给管理员 / 运营人员指南 (Operator Guide)

1.1 活动本质与产品定位

好运探索季是 NGSS 针对高黏性活跃与长线留存设计的全新活动类型，与现行付费的幸运转盘（Lucky Wheel）并列并存，绝不替代幸运转盘。

核心产品目标：让玩家始终感受到「快要完成、而且数学上真的可以完成」，消除「永远差 0.01 刀」的挫败感，通过确定性推进激发长期做任务与社交促活。

1.2 玩家核心体验闭环 (Player Loop)

  1. 参加起点：玩家点击「参加活动」，初始进度明确展示为 0%，建立当前活动配置快照。
  2. 首转飞跃：成功进行第 1 次转动，进度条瞬间跃升至后台设定的首转进度（建议默认 90%），大幅点燃玩家期待。
  3. 获取抽奖次数：通过「每日免费抽」、「完成指定游戏或充值任务」、「邀请好友助力」三种独立途径获取抽奖次数。
  4. 阶段性出奖：后续转动在「快砍（主要现金）」→「中段（主要积分）」→「细砍（主要点数）」中渐进开奖，并可能触发「越级加成」。
  5. 终点满奖：在达到所属层级的目标转数 T 时，进度精确达到 100%，自动发放转满大奖（现金），本局顺利结案并关闭。

1.3 关键规则防坑指南（红线规范）

前台严禁展示「还差几次」：后台有明确的目标转数 T 与数学曲线，但前台界面绝不展示还差几次完成，避免形成法律承诺或导致玩家倒算成本。前台仅展示「当前进度 %」与「获取抽奖次数」的任务入口。

完成率是运营规划估算，绝非暗抽胜率：后台显示的完成率（如 69%）是系统根据玩家历史回访概率与任务完成率进行的离散分布卷积模拟，代表有多少人能拿齐 T 次；绝对不是给玩家暗抽「中/不中」。

3.3 确定性进度公式与唯一阶段函数

确定性进度函数：给定快照的 $F, T, \gamma$，进度 $P(k)$ 在任何节点均由确定性数学公式产出： 

P(0) = 0
P(1) = F
P(T) = 100
for 1 < k < T:
  q = (k - 1) / (T - 1)
  P(k) = F + (100 - F) * (1 - (1 - q)^γ)

阶段整数分配（Hamilton 最大余数法）： 第 1 转固定为快砍。其余 $T-1$ 转中，先分配 fast、mid、fine 各 1 转底限，剩余配额按归一化比例使用 Hamilton 法分配，确保三个模块无论在前台预览、开奖还是预算预留中完全使用同一 phaseOf(k, T, shares) 函数。

4. 单事务原子抽奖流程 (One-Transaction Spin Architecture)

服务端 POST /api/lucky-journey/spin 执行步骤必须在严格的数据库本地事务内完成：

  1. 请求幂等校验：检查 requestId 是否在 SpinRecord 中已存在。若存在，直接提交事务并返回原有记录，绝不重复扣减次数与重抽奖励。
  2. 行级锁锁定 Play：SELECT * FROM Play WHERE playId = :id FOR UPDATE。校验 status === 'active' 且 ticketsAvailable >= 1。
  3. 自增转数校验：计算当前步数 $k = \text{spinIndex} + 1$。若 $k > \text{effectiveTargetSpins}$，直接拒绝。
  4. 确定性计算进度：计算 $\text{progressAfter} = P(k)$，增量 $\Delta = \text{progressAfter} - \text{progressBefore}$。
  5. 服务端安全 RNG 抽奖：使用系统安全随机数源（CSPRNG）抽取奖品类型（谢谢参与 / 越级 / 本段主奖）及金额档位（小/中/大）。
  6. 扣减次数与落库：更新 play.ticketsAvailable -= 1，play.spinIndex = k，play.progressBp = progressAfter。
  7. 终点奖励判定：若 $k = \text{effectiveTargetSpins}$，且此前未发过终点奖，生成终点大奖派发单 RewardGrant(spinId:finish)，并将 play.status = 'completed'。
  8. 预算责任释放：扣减本转对应的预留上限 liabilityReserved -= maxForThisSpin，并将实际产生金额累加至 BudgetLedger.actualSpent。
  9. 事务提交与 Outbox 派发：提交事务，异步通过 Outbox 事件将现金/积分派发给钱包适配器。

5. 40 项情境与异常处理表 (Situations & Edge Cases S01~S40)

ID 业务场景 V3 规范执行行为 设计依据
S01 活动进行中点击参加 校验层级资格与预算预留，快照当前配置版本，创建 Play，初始进度严格为 0%。 真实起始
S02 活动时间结束后点击参加 API 拒绝并提示「活动已截止」，不创建 Play，不扣资源。 准入控制
S03 次数为 0 点击转盘 HTTP 409 / 业务拒绝，不扣次、不抽奖、不推进度，引导完成任务。 状态拦截
S04 第一转成功结算 进度精确到达 firstSpinPct（如 90%）；阶段为快砍；奖励依据快砍概率抽发。 体验爽感
S05 第 2 转至 T-1 转推进 进度严格按照曲线公式 $P(k)$ 计算；阶段严格按照 Hamilton phaseOf 判定。 确定性推进
S06 中段开出主奖励 发放活动积分；若触发越级加成，则直接开出快砍现金金额。 跨级激励
S07 细砍开出主奖励 发放活动点数；若触发越级加成，开出中段积分金额（细砍不连跳至现金）。 经济稳健
S08 抽中「谢谢参与」 本转无代币奖励入账，但确定性进度正常推进，绝不空耗次数。 正向反馈
S09 达到有效转数 k = T 进度精确收尾至 100.00%；触发并发放转满大奖（现金）；状态置为 completed。 无死锁通极大奖
S10 达成 100% 后剩余次数 主按钮锁定，API 拒绝继续抽奖；剩余次数标记为失效，不可继续开奖。 责任边界
S11 同 requestId 请求重试 命中幂等缓存，直接返回历史 SpinRecord，不重复扣次与出奖。 幂等性
S12 多端并发点击转盘 Play 行级悲观锁串行化处理；先到者成功执行，后者读新状态处理。 并发控制
S13 抽奖成功后网络断线 服务端已落库；客户端重连后凭同一 requestId 或查询状态直接恢复结果。 连接容灾
S14 派奖钱包服务暂时不可用 抽奖记录正常持久化，RewardGrant 标记为 pending，Outbox 持续重试派奖。 异步解耦
S15 好友完成合格注册 仅为邀请人增加抽奖次数，绝不直接改变邀请人的进度条。 助力机制
S16 开启充值门槛但好友未充值 下线仅注册时不发放助力次数，待好友充值成功结算后方才授予。 防刷门槛
S17 好友与外部推广返佣同时发生 好运探索季只记录本活动的 TicketLedger，两者独立计奖，不相互冲突。 多业务共存
S18 活动运行中运营中途修改配置 已在局内的 Play 继续沿用当时快照的 configVersionId，仅新加入 Play 采用新版。 配置版本化
S19 某项任务被运营关闭 新产生的该行为不再发次数，已发次数不受影响。 动态管控
S20 游玩指定类型游戏 仅统计单选配置的指定游戏类别（如电子），其他类别不予计入。 单选任务
S21 高 VIP 会员点击参加 依据分层配置赋予更小的有效转数 T（如 8 转），首转同样为 90%。 有效 T 驱动
S22 局内中途升级 VIP 或充值 V3 默认本局有效 T 保持快照不变，下一轮新 Play 自动匹配新高层级。 快照稳定性
S23 活动预算或名额耗尽 新玩家点击「参加活动」提示名额已满；局内老玩家正常完成，体验不受影响。 预算硬预留
S24 运营修改曲线曲率 γ 只影响修改后产生的新 Play，老玩家曲线绝不突变。 一致性保障
S25 允许重复参加开启新一轮 上一局 completed 后允许开新局，进度重归 0%；当日免费次数不可重复申领。 租户日去重
S26 新一局的任务统计 仅累计新局 joinedAt 之后发生的新结算，上一局充值累计不可穿透。 作用域隔离
S27 同一下线在第二局重复助力 拒绝发放，同一受邀下线在全活动生命周期内仅可贡献 1 次。 全活动唯一
S28 活动大时间截止 (afterEnd=cut) 强行关闭在玩 Play，清空未用次数，释放剩余未开预留责任，不补发大奖。 截断策略
S29 活动大时间截止 (afterEnd=finish) 停止新玩家加入，但局内玩家可继续做任务推进至个人截止日并领大奖。 做完策略
S30 个人窗口 (personalDays) 过期 自动结案关闭，未转出的未用次数失效，已派发奖励正常归属。 个人生命周期
S31 运营将总预算调低至已承诺责任以下 后台校验阻断并报错，禁止保存低于 actualSpent + outstandingReserve 的预算。 预算防击穿
S32 运营追加总预算 可用余额增加，系统自动重新开放新名额参加。 动态扩容
S33 运营修改阶段划分比例 新局采用新阶段分配计划，老局按原分配执行。 规则隔离
S34 配置出现 thanks + upgrade > 100% 后台红灯拦截，禁止发布活动配置。 绝对概率合规
S35 总供给次数小于任一分层的有效 T 后台红灯拦截，数学上不可完成的活动禁止发布。 可行性硬阻断
S36 非社交路径不足但开启了保证模式 后台由黄灯升级为红灯阻断，确保无需拉人即可完成。 社交免受迫
S37 配置「打开活动页即参加」 后台出现强警告，并强制要求配置参与人数上限与足额预算。 高危防范
S38 充值发生退款或注单作废 任务仅在 settled 且不可逆状态发放；如遇极端恶意逆转依风控白名单处置。 资产安全
S39 风控检测到设备/IP 刷子 风控拦截后续抽奖发放或转入人工审查，绝不偷偷修改已生成的 SpinRecord。 数据真实
S40 前端罗盘动画卡死或异常 玩家可点击跳过动画，前端直接拉取服务端 SpinRecord 展示权威真实结果。 容错韧性
